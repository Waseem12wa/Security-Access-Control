1. Overview (brief)
This project implements an access-controlled system using:
1) Users with unique IDs and Roles (GUEST, STUDENT, STAFF, ADMIN),
2) Resources with AccessScope (PUBLIC, INTERNAL, CONFIDENTIAL),
3) Access rules (policy) that decide ALLOW/REFUSE for READ/WRITE,
4) Typed capabilities using Java Generics to enforce that only the correct operation can be invoked at compile time,
5) Logging of every authorization decision (including timestamp, user, role, resource, operation, and ALLOW/REFUSE).

Core implementation highlights:
- Authorization is evaluated using a rule-chain (Chain of Responsibility style).
- Logging is added via a decorator (so policy logic remains separate from logging).
- All main access points use generics-typed capabilities: read accepts Capability<Read>, and write accepts Capability<Write>.

3. Design Patterns (Up to 2) [04 marks]

| Design Pattern Name | Involved classes/methods | Justification |
|---|---|---|
| Chain of Responsibility (rule chain) | `RuleChainAccessAuthorizer.authorize(...)`, `AccessRule.evaluate(...)`, `GuestAccessRule`, `StudentAccessRule`, `StaffAccessRule`, `AdminAccessRule` | Authorization is decided by trying a sequence of modular rules. 10. Implementation Inspection (D) - copy for live demo [not part of tables]

Most challenging design pattern: Chain of Responsibility (rule chain)
- Implemented by: `com.coursework.accesscontrol.auth.RuleChainAccessAuthorizer#authorize(...)`
- Supporting code:
  - `com.coursework.accesscontrol.auth.rules.AccessRule`
  - `GuestAccessRule`, `StudentAccessRule`, `StaffAccessRule`, `AdminAccessRule`
- Explanation:
  The authorizer iterates through an ordered list of rules. Each rule’s `evaluate(...)` returns `Optional<AccessResult>`.
  - `Optional.empty()` means: rule does not apply (try next rule)
  - `Optional.of(...)` means: a decision is found (first-match)
  If no rule provides a decision, the authorizer returns `REFUSE` by default.
  This makes the authorization logic modular and safer, because “no matching rule” results in denying access.

Most challenging JUnit test: `studentDeniedWriteConfidentialAndLogged`
- Implemented by: `com.coursework.accesscontrol.AccessControlPolicyTest#studentDeniedWriteConfidentialAndLogged`
- What it validates:
  1) The policy decision for STUDENT attempting WRITE on a CONFIDENTIAL resource is `REFUSE`.
  2) The secure service does not modify the resource content when access is refused.
  3) The log entry is created with `REFUSE` and includes the correct resource name and userId.
